# Tortuga features

> Features that are implemented **and verified**, by requirement ID, and (at the end, under
> [Agreed requirements](#agreed-requirements)) the requirements they were built to. Open work and new
> requirements are in [ROADMAP.md](ROADMAP.md).
>
> Add an entry only when the requirement is fully met, has automated tests where practical, and has
> been checked in the running app on at least one OS. Note which OSes were checked. Then move the
> requirement's row from the roadmap to "Agreed requirements".

**Verified on:** Linux = Ubuntu 24.04 under WSL2/WSLg (desktop build). Windows: start-up only (M7). macOS has not been run yet.

**UI rewrite (2026-10-16):** the UI moved from Dioxus to egui (`tortuga-ui-egui`). The engine and file formats did
not change. Re-checked in the running egui app (Linux, X11 via WSLg): sending, URL/params sync, pretty JSON,
status colours, headers tab, "Save to file…" (byte-identical), cancel, settings + TLS banner (saved to disk),
collection tree, selection, new folder (starts in rename mode), inline rename, duplicate, move up, move to,
delete with confirmation, unsaved marker + Ctrl+S + Ctrl+Enter, broken-file error, environments dialog (files on
disk), environment picker, undefined-variable highlight and send block, 5 MB body truncation, collections reopened
after a restart. Not yet re-checked in the egui app: the body editor types and sending through a server base URL.
(Creating and adding projects was checked with M6.5.)

### HTTP requests

| ID | Requirement |
|---|---|
| R-HTTP-1 | Methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`. |
| R-HTTP-2 | URL editor; query parameters also editable as a key/value table, kept in sync with the URL. Each param can be disabled without deleting it. |
| R-HTTP-3 | Headers as a key/value table; each header can be disabled. Duplicate header names are allowed. |
| R-HTTP-4 | Body types: none, raw text, JSON, `x-www-form-urlencoded`. Content-Type is set automatically unless overridden. |
| R-HTTP-5 | Auth: none, Basic, Bearer token. Set per request, or inherited from the collection. |
| R-HTTP-6 | Response view: status, time, size, headers, body. JSON bodies are pretty-printed; others shown as text; binary bodies can be saved to a file. |
| R-HTTP-7 | An in-flight request can be cancelled. Per-request timeout with a global default. |
| R-HTTP-9 | Copy a request as a `curl` command with variables resolved. Secret values are masked unless the user confirms including them. *(D1; was IDEA-4)* |
| R-HTTP-10 | Path variables: a URL path segment starting with `:` (e.g. `/users/:id`) is a path variable. Its value is edited in a table that follows the URL, may contain `{{variables}}`, is URL-encoded when sent, and is saved in the request file. Sending stops with a message naming any path variable without a value. Only the path counts, so `host:8080` is not a variable. |
| R-HTTP-11 | **Paste a `curl` command** into the URL field to fill the current request: method, URL and query params, headers, body (JSON, form or text), Basic auth (`-u`) and timeout (`-m`). | R-HTTP-12 | **Search in the response body** (Ctrl+F while the response is shown, or the search field above it): matches are highlighted, "n of m" is shown, Enter / Shift+Enter go to the next / previous match and scroll to it. Case-insensitive. Searches the shown text (the first 2 MB of big bodies). *(IDEA-30)* |
| R-HTTP-13 | **Filter JSON responses** with a JSONPath expression (D18): `$`, `.name`, `['name']`, `[n]` (negative counts from the end), `[a:b]`, `[*]`, `..name`, `[a,b]`, and filters `[?(@.field)]` / `[?(@.field <op> value)]` with `== != < <= > >=`. The matches are shown pretty-printed; an invalid expression is explained. The filter is kept per request while the app runs, so a new response is filtered the same way. Works on bodies of any size: it runs off the UI thread. *(IDEA-30)* |
| R-HTTP-14 | **Preview** tab in the request editor: the request exactly as it will be sent (method, full URL, every header including inherited ones, Content-Type and Authorization, body), with variables, server and path variables resolved and secret values masked as `<secret:name>`. Undefined variables are named instead. Updates while typing. *(IDEA-7)* |
| R-HTTP-15 | **`multipart/form-data` bodies**: a list of parts, each with a name and either a text value or a file to upload; parts can be switched off; names, values and file paths may use `{{variables}}`. A file inside the project folder is saved relative to it, so teammates can send the request too; a file elsewhere keeps its full path and is marked as working only on this computer (D21). The file is read when sending; a missing file stops the send with a message naming it. A part can set its own content type. A directory with files to upload but no requests (and no `_folder.toml`) is not shown as a folder. "Copy as curl" writes `-F`/`--form-string`; pasting curl reads them (R-HTTP-9, R-HTTP-11). *(IDEA-2)* |
| R-HTTP-16 | **Custom CA certificates**: in Settings, the user adds PEM files (each may hold several certificates) whose certificates are trusted in addition to the system's, e.g. for internal APIs signed by a company CA. They are local settings, not shared (D22). A file that can't be read or holds no certificate is reported naming it, and the others still apply. *(IDEA-3)* |
| R-HTTP-17 | **Image responses are shown as pictures** in the Body tab (PNG, JPEG, GIF, WebP, BMP, ICO), scaled down to fit the panel, with their format and size in pixels. An image is recognised by its bytes, so a wrong content type does not matter. Decoding runs off the UI thread and refuses images too large to decode safely. |
| R-HTTP-18 | **Raw body view**: a switch above the body between the formatted view ("Pretty", or "Preview" for images and binary content) and "Raw": the body as it came (unformatted JSON), or for images and binary content a hex dump of the first 256 KB. The choice is kept for the next response. Bodies that are shown as they came anyway (plain text) have no switch. |
| R-HTTP-19 | **XML requests and responses**, on a par with JSON. An **XML body type** that sends `application/xml` unless the user sets a Content-Type, is checked as you type (what is wrong, line and column) and has a Beautify button; saved as `kind = "xml"`. Responses whose Content-Type says XML (`application/xml`, `text/xml`, `+xml` types such as SOAP), or that have none and parse as XML, are **pretty-printed** (two-space indents, text-only elements on one line, comments and CDATA as written), with "Raw" showing them as they came (R-HTTP-18). The curl, Postman and `.http` imports make XML bodies from an XML Content-Type or Postman's "xml" language. |
| R-HTTP-20 | **Proxy setting** (Settings → Requests → Proxy; D54): from the system (default, as R-HTTP-8), none (straight to the server, whatever the system says), or manual: a proxy URL (`http://` or `https://`; `127.0.0.1:8080` means `http://127.0.0.1:8080`) and hosts that bypass it, one per line (`example.com` and `*.example.com` both cover its subdomains, `10.0.0.0/8` a network). | R-HTTP-21 | **Move query params into the body.** When the method changes from GET to one that sends a body (POST, PUT, PATCH, DELETE) while the request has query parameters and no body, a line under the URL offers to move them into the body as **JSON** or **XML**, or **Keep in URL**. JSON is an object with a key per parameter: a value written as a JSON number or `true`/`false` keeps that type (`01` and `1e3` stay text), a name used more than once becomes an array. XML is a `<request>` element with an element per parameter in order, characters a tag name can't hold becoming `_`. Only switched-on parameters move; the URL and the Body tab show the result at once, and Revert undoes it like any edit. The offer goes away once a body exists, the parameters are gone or the method is GET again. |
| R-HTTP-22 | **Header auth.** The Auth tab (request, folder, project and workspace defaults) gets a fourth kind, **Header**: a header name and a value, e.g. `X-API-Key: {{api_key}}`, both taking `{{variables}}`. The value is masked and warned about like a Basic password or Bearer token (R-HTTP-5); a header of the same name added by hand wins; without a name no header is sent. Saved as `kind = "header"` with `name` and `value`. |
| R-HTTP-23 | **Automatic headers.** Every send (app, workflows, CLI) gets `User-Agent: Tortuga/<version>`, `Accept: */*`, `Accept-Encoding: gzip, deflate, br`, `Cache-Control: no-cache` and `X-Tortuga-Token`: a new CUID2 for each send, so one send can be found in a server's logs. An enabled header of the same name (any case) on the request, its folders, project or workspace wins, also with an empty value; a disabled one doesn't count. `Host`, `Content-Length` and the connection's headers are left to the transport. The Preview (R-HTTP-14) lists them after the request's own headers, the token as "(a new CUID2 for each send)". |
| R-HTTP-24 | **JSON and XML in colour.** The request body editor (JSON and XML body types) and the response's pretty view (JSON and XML, also when filtered or too big to format) colour keys and element names, strings and attribute values, numbers, `true`/`false`/`null` and entities, attribute names, and dim punctuation and comments (XML comments, declarations, `<!DOCTYPE>`); a `{{variable}}` gets its own colour, also inside a string. Colouring is lenient: half-typed, invalid or truncated text is coloured as far as it reads. The raw view (R-HTTP-18) and plain text stay uncoloured, and search matches (R-HTTP-12) are highlighted over the colours. Colours come from the theme, so they suit light and dark mode. Bodies over 200 KB are not coloured while editing. |

### Collaboration through git

#### On-disk format

Example layout:
```
my-api/                    # collection root, typically inside the API's git repo
  tortuga.toml             # manifest: name, format version, servers, collection variables
  environments/
    dev.toml
    staging.toml
  users/                   # a folder
    _folder.toml           # optional: folder display name and position (seq)
    list-users.toml
    create-user.toml
```
Example manifest and environment:
```toml
# tortuga.toml
format = 1
name = "Acme API"
[[servers]]
id = "users"               # stable key used by requests; the name can change freely
name = "Users API"
[variables]                # collection defaults
api_version = "v2"
```
```toml
# environments/dev.toml
name = "Development"
seq = 1
[servers]
users = "http://localhost:8080"
[variables]
user_id = "42"
```
Example request file:
```toml
name = "Create user"
seq = 2
method = "POST"
server = "users"
url = "/users"
[[headers]]
name = "Accept"
value = "application/json"
[body]
kind = "json"
content = '''
{
  "name": "{{user_name}}"
}
'''
```

| ID | Requirement |
|---|---|
| R-GIT-1 | A collection is a directory and can live anywhere, inside or outside a git repo. Folders are directories. |
| R-GIT-2 | **One TOML file per request**, so concurrent edits to different requests never conflict. |
| R-GIT-3 | Output is deterministic, so saving an unchanged request never modifies its file. Key order is fixed, and only fields that differ from their defaults are written. |
| R-GIT-4 | Shared files hold only shared data. No timestamps, response history, window/UI state, cookies, or secret values. |
| R-GIT-5 | File names come from request names (e.g. `create-user.toml`). Renaming a request renames its file, so git sees a rename. |
| R-GIT-6 | Order is stored as a `seq` number in each request file, not in a central list, so two people adding requests don't both edit the same file. |
| R-GIT-7 | The collection manifest `tortuga.toml` holds a `format` version. Newer app versions migrate older formats. If a file uses a newer format than the app understands, it is shown read-only. |
| R-GIT-8 | Files are hand-editable. A file that fails to parse (e.g. it contains merge-conflict markers) is shown as an error on that item only; the rest of the collection still loads. |

### Mock APIs

| ID | Requirement |
|---|---|
| R-MOCK-1 | **Examples on a request** (D44). A request holds named example responses: status, headers and a text body (its Content-Type header says what it is, else JSON, XML or text is worked out from the body), saved in its request file as `[[examples]]` (`name`, `status`, `delay_ms`, `body`, `headers`, and the `match` conditions of R-MOCK-3). An **Examples** tab in the request editor (requests of a project) lists them and adds, edits, reorders and removes them. **Save as example** in the response panel saves the last response under a free name such as "200 OK"; `Authorization`, `Cookie`, `Set-Cookie`, `Content-Length`, `Transfer-Encoding`, `Connection` and `Date` are left out (P6). Examples follow a request when it is renamed, moved or duplicated. Request files without examples load as before; builds before this one drop examples when they save the request. |
| R-MOCK-2 | **Mock server.** "Start mock server" (project menu and command palette) serves the project's examples on `127.0.0.1`, on the port it last used or else the first free one from 4010 (kept per project in local data; changed in the mock server dialog). "Stop mock server" ends it; the project row shows `mock :<port>` while it runs, and closing the project stops it. An incoming request is answered by a saved request with the same method whose URL path, after its server's base URL (or after the scheme and host, or a leading `{{variable}}`, for requests without a server), matches: `:name` and `{{name}}` segments match any one segment, and the request with more literal segments wins, then the first in the tree. With several servers, a path that starts with `/<server id>` is matched against that server's requests first. The answer is the chosen example's status, headers and body, with `{{variables}}` filled from the active environment (never secret values); an example HTTP can't carry is a `500` saying why. With no matching request, a match without examples, or no example whose conditions hold, the answer is `404` with a JSON body giving the reason and the closest requests, so a developer sees what is not defined yet. Matching lives in `tortuga-core` (it compiles for wasm); the listener is native only, on `hyper` (D46). The mock listens on localhost only and contacts no other host (R-P-4). In the app it serves the files as they are on disk: a saved edit or a `git pull` changes the next answer. |
| R-MOCK-3 | **Choosing an example.** Of a request's examples, the first in file order whose `match` conditions all hold answers: `query` and `headers` (name and value), and `body` (a JSONPath (R-HTTP-13) or `xpath:` (R-HTTP-19) expression with the value it must have). An example without conditions matches anything, so the last one is the usual fallback. A request header `X-Tortuga-Example: <name>` picks an example by name, so a test can ask for the error case. `delay_ms` holds the answer back, to try slow responses. |
| R-MOCK-4 | **Sending to the mock** (D45). While a mock runs, the environment picker and the command palette offer **Mock (port N)**: an environment that is never saved, in which every server's base URL is its project's mock (under `/<server id>` when the project has several servers) and the variables keep the values of the environment chosen before. Projects without a running mock keep their environment; requests with a full URL and no server are sent as written. Choosing another environment, or stopping the last mock, ends it. The **mock server dialog** (project menu → "Mock server (port N)…") shows whether it runs and on which port, starts, stops or moves it to another port, offers "Send requests here", and lists what it received, newest first: time, status, method and path, and the request and example that answered, or why nothing did (the last 500). |
| R-MOCK-5 | **Mocks in automated tests.** `tortuga-cli mock <project> [--port N] [--env NAME]` serves the mock (default port 4010) until stopped (Ctrl+C) and prints one line per request it answers. `tortuga-cli run <project> [target] --mock [--port N]` starts the mock on a free port, runs the workflow, folder or request with every server pointing at it (as R-MOCK-4, with the variables of `--env` if given) and stops it again, so a workflow's tests run in CI against the API as designed, before it exists. A request the mock could not answer fails its step (a `404`), and the reason is printed under it. Exit codes as R-CLI-1. |
| R-MOCK-6 | **Examples from OpenAPI.** The OpenAPI import (R-COL-15) turns each operation's responses into the request's examples: each named example of the preferred media type (JSON first) under its key, else one from `example` or built from the schema, named by the code; a response without content gives an example without a body; `4XX`-style codes become `400`, `default` is left out. | R-MOCK-7 | **Tortuga tests itself with Tortuga.** The repository has a workspace, `selftest/tortuga-selftest.tortuga-workspace.toml`, with projects whose requests carry examples (R-MOCK-1) whose conditions only hold when the request was sent exactly right, and workflows with tests. A test in `tortuga-cli` runs every workflow of every project in it with `tortuga-cli run … --mock --workspace …` (R-MOCK-5), so `cargo test`, `make verify` and CI fail when a change breaks sending, auth, variables, captures, scripts, the file format or the mock; `make selftest` runs only those. `selftest/README.md` says which requirements each project covers. |
| R-MOCK-8 | **Contract check** (D47). After a response to a request that has examples (R-MOCK-1), it is compared with the example it should match: of the examples with the response's status, the first whose `match` conditions (R-MOCK-3) hold for the request as sent, else the first. Compared: the **status** is one of the examples' (otherwise "Status 500 is not one of the examples' (200, 404)"); the **Content-Type**'s media type (case and parameters ignored) is the example's, when the example has a Content-Type header or a body (then guessed as in R-MOCK-2); and for JSON, the **shape**: every key of an example object is in the response with a value of the same JSON type (string, number, boolean, array, object), a key the response has and the example lacks is reported too, `null` in the example accepts any value, and every element of a response array is checked against the example array's first element. Values and key order are not compared, so differences never show response data (P6). The example body's `{{variables}}` are filled first; one that is still not JSON is checked for status and Content-Type only. Differences name their place as JSONPath (`$.items[2].id is a string, the example has a number`, `$.total is missing`, `$.debug is not in the example`). The outcome is one test result, **Matches example “200 OK”**, passed or failed with the differences (the first 20, then "and N more"), in the Tests tab and its count (R-TEST-6, R-TEST-11). In the app a send and Re-run tests (R-TEST-12) check; workflows check only with `tortuga-cli run --check-examples`, where a difference fails the step like a failed test and is in the reports (R-CLI-3). Requests without examples are not checked. *(IDEA-56)* |
