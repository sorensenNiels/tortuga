# Tortuga requirements

> The agreed text of every requirement that is implemented **and verified**: when one is, its row moves here from
> [ROADMAP.md](ROADMAP.md) (open requirements) and [FEATURES.md](FEATURES.md) records how it was verified.
> Look a requirement up by ID (`grep -n "R-COL-3 " docs/REQUIREMENTS.md`) rather than reading the whole file.

The requirements the features in FEATURES.md were built to, as agreed in [ROADMAP.md](ROADMAP.md) (moved here on
2026-10-18, when Phase 2 was done, and the Phase 3 ones the same day when it was done). Open ones are still in the roadmap.

## Principles

| ID | Requirement |
|---|---|
| R-P-1 | **Local-first.** All data are plain files the user owns. No account, login, or cloud service is needed. |
| R-P-2 | **Git is the collaboration layer.** Teams share collections by committing them to a git repository, often next to the API source code. The on-disk format is effectively our public collaboration API. |

## HTTP requests

| ID | Requirement |
|---|---|
| R-HTTP-1 | Methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`. |
| R-HTTP-2 | URL editor; query parameters also editable as a key/value table, kept in sync with the URL. Each param can be disabled without deleting it. |
| R-HTTP-3 | Headers as a key/value table; each header can be disabled. Duplicate header names are allowed. |
| R-HTTP-4 | Body types: none, raw text, JSON, `x-www-form-urlencoded`. Content-Type is set automatically unless overridden. |
| R-HTTP-5 | Auth: none, Basic, Bearer token. Set per request, or inherited from the collection. |
| R-HTTP-6 | Response view: status, time, size, headers, body. JSON bodies are pretty-printed; others shown as text; binary bodies can be saved to a file. |
| R-HTTP-7 | An in-flight request can be cancelled. Per-request timeout with a global default. |
| R-HTTP-9 | Copy a request as a `curl` command with variables resolved. Secret values are masked unless the user confirms including them. *(D1; was IDEA-4)* |
| R-HTTP-10 | Path variables: a URL path segment starting with `:` (e.g. `/users/:id`) is a path variable. Its value is edited in a table that follows the URL, may contain `{{variables}}`, is URL-encoded when sent, and is saved in the request file. Sending stops with a message naming any path variable without a value. Only the path counts, so `host:8080` is not a variable. |
| R-HTTP-11 | **Paste a `curl` command** into the URL field to fill the current request: method, URL and query params, headers, body (JSON, form or text), Basic auth (`-u`) and timeout (`-m`). It becomes unsaved edits (Revert undoes it, D19). If the URL starts with a server's base URL in the active environment, that server is chosen and the URL keeps only the path. Options Tortuga can't use (e.g. `-F`, `-k`) are listed in a notice. Bash/zsh quoting and line continuations are understood (what browsers' "Copy as cURL (bash)" produces). *(IDEA-28, D7)* |
| R-HTTP-12 | **Search in the response body** (Ctrl+F while the response is shown, or the search field above it): matches are highlighted, "n of m" is shown, Enter / Shift+Enter go to the next / previous match and scroll to it. Case-insensitive. Searches the shown text (the first 2 MB of big bodies). *(IDEA-30)* |
| R-HTTP-13 | **Filter JSON responses** with a JSONPath expression (D18): `$`, `.name`, `['name']`, `[n]` (negative counts from the end), `[a:b]`, `[*]`, `..name`, `[a,b]`, and filters `[?(@.field)]` / `[?(@.field <op> value)]` with `== != < <= > >=`. The matches are shown pretty-printed; an invalid expression is explained. The filter is kept per request while the app runs, so a new response is filtered the same way. Works on bodies of any size: it runs off the UI thread. *(IDEA-30)* |
| R-HTTP-14 | **Preview** tab in the request editor: the request exactly as it will be sent (method, full URL, every header including inherited ones, Content-Type and Authorization, body), with variables, server and path variables resolved and secret values masked as `<secret:name>`. Undefined variables are named instead. Updates while typing. *(IDEA-7)* |
| R-HTTP-15 | **`multipart/form-data` bodies**: a list of parts, each with a name and either a text value or a file to upload; parts can be switched off; names, values and file paths may use `{{variables}}`. A file inside the project folder is saved relative to it, so teammates can send the request too; a file elsewhere keeps its full path and is marked as working only on this computer (D21). The file is read when sending; a missing file stops the send with a message naming it. A part can set its own content type. A directory with files to upload but no requests (and no `_folder.toml`) is not shown as a folder. "Copy as curl" writes `-F`/`--form-string`; pasting curl reads them (R-HTTP-9, R-HTTP-11). *(IDEA-2)* |
| R-HTTP-16 | **Custom CA certificates**: in Settings, the user adds PEM files (each may hold several certificates) whose certificates are trusted in addition to the system's, e.g. for internal APIs signed by a company CA. They are local settings, not shared (D22). A file that can't be read or holds no certificate is reported naming it, and the others still apply. *(IDEA-3)* |
| R-HTTP-17 | **Image responses are shown as pictures** in the Body tab (PNG, JPEG, GIF, WebP, BMP, ICO), scaled down to fit the panel, with their format and size in pixels. An image is recognised by its bytes, so a wrong content type does not matter. Decoding runs off the UI thread and refuses images too large to decode safely. |
| R-HTTP-18 | **Raw body view**: a switch above the body between the formatted view ("Pretty", or "Preview" for images and binary content) and "Raw": the body as it came (unformatted JSON), or for images and binary content a hex dump of the first 256 KB. The choice is kept for the next response. Bodies that are shown as they came anyway (plain text) have no switch. |
| R-HTTP-19 | **XML requests and responses**, on a par with JSON. An **XML body type** that sends `application/xml` unless the user sets a Content-Type, is checked as you type (what is wrong, line and column) and has a Beautify button; saved as `kind = "xml"`. Responses whose Content-Type says XML (`application/xml`, `text/xml`, `+xml` types such as SOAP), or that have none and parse as XML, are **pretty-printed** (two-space indents, text-only elements on one line, comments and CDATA as written), with "Raw" showing them as they came (R-HTTP-18). The response **filter takes an XPath subset** above XML bodies (D40): `/`, `//`, names (a name without a prefix matches any prefix), `*`, `@name`, `@*`, `text()`, `node()`, `.`, `..`, and predicates `[n]`, `[last()]`, `[last()-n]`, `[path]`, `[path <op> literal]` with `= != < <= > >=`; elements are shown pretty-printed, attributes and text as their values; it runs off the UI thread on the whole body. **Captures** take `xpath:<expression>`: the text of the first match (R-TEST-4). The curl, Postman and `.http` imports make XML bodies from an XML Content-Type or Postman's "xml" language. |
| R-HTTP-20 | **Proxy setting** (Settings → Requests → Proxy; D54): from the system (default, as R-HTTP-8), none (straight to the server, whatever the system says), or manual: a proxy URL (`http://` or `https://`; `127.0.0.1:8080` means `http://127.0.0.1:8080`) and hosts that bypass it, one per line (`example.com` and `*.example.com` both cover its subdomains, `10.0.0.0/8` a network). A URL with a user name or password is refused, and Save stays off while the manual URL can't be used, saying why on every tab. Errors never repeat the URL. Local setting; `tortuga-cli` keeps using the system proxy and `HTTP_PROXY`-style variables. *(IDEA-88)* |
| R-HTTP-21 | **Move query params into the body.** When the method changes from GET to one that sends a body (POST, PUT, PATCH, DELETE) while the request has query parameters and no body, a line under the URL offers to move them into the body as **JSON** or **XML**, or **Keep in URL**. JSON is an object with a key per parameter: a value written as a JSON number or `true`/`false` keeps that type (`01` and `1e3` stay text), a name used more than once becomes an array. XML is a `<request>` element with an element per parameter in order, characters a tag name can't hold becoming `_`. Only switched-on parameters move; the URL and the Body tab show the result at once, and Revert undoes it like any edit. The offer goes away once a body exists, the parameters are gone or the method is GET again. |
| R-HTTP-22 | **Header auth.** The Auth tab (request, folder, project and workspace defaults) gets a fourth kind, **Header**: a header name and a value, e.g. `X-API-Key: {{api_key}}`, both taking `{{variables}}`. The value is masked and warned about like a Basic password or Bearer token (R-HTTP-5); a header of the same name added by hand wins; without a name no header is sent. Saved as `kind = "header"` with `name` and `value`. |
| R-HTTP-23 | **Automatic headers.** Every send (app, workflows, CLI) gets `User-Agent: Tortuga/<version>`, `Accept: */*`, `Accept-Encoding: gzip, deflate, br`, `Cache-Control: no-cache` and `X-Tortuga-Token`: a new CUID2 for each send, so one send can be found in a server's logs. An enabled header of the same name (any case) on the request, its folders, project or workspace wins, also with an empty value; a disabled one doesn't count. `Host`, `Content-Length` and the connection's headers are left to the transport. The Preview (R-HTTP-14) lists them after the request's own headers, the token as "(a new CUID2 for each send)". |
| R-HTTP-24 | **JSON and XML in colour.** The request body editor (JSON and XML body types) and the response's pretty view (JSON and XML, also when filtered or too big to format) colour keys and element names, strings and attribute values, numbers, `true`/`false`/`null` and entities, attribute names, and dim punctuation and comments (XML comments, declarations, `<!DOCTYPE>`); a `{{variable}}` gets its own colour, also inside a string. Colouring is lenient: half-typed, invalid or truncated text is coloured as far as it reads. The raw view (R-HTTP-18) and plain text stay uncoloured, and search matches (R-HTTP-12) are highlighted over the colours. Colours come from the theme, so they suit light and dark mode. Bodies over 200 KB are not coloured while editing. |
| R-HTTP-25 | **Where the time went.** The time in the response line opens a breakdown of the send (D68): DNS lookup, Connect + TLS, Waiting for the server (sending the request and the server's work) and Download, each as a bar in a waterfall with its time, and below them the total, the HTTP version and whether the connection was new or reused. A reused connection has no lookup or connecting, an IP address no lookup; with redirects followed each phase is the sum over every hop. The web build shows only waiting and download, which is what the browser tells. A response from history has no breakdown, and its time stays plain text. *(IDEA-104)* |

### History

| ID | Requirement |
|---|---|
| R-HIST-1 | Every sent request is kept in a **local history** (§6.7) per project, and one for the scratch request: when it was sent, the environment, the request as it was in the editor, and the response (status, time, size, headers, body). The last 200 entries per project are kept; bodies over 1 MB are cut to 1 MB. Like unsaved edits, history may hold credentials typed into a request, so it is readable only by the user. *(IDEA-5)* |
| R-HIST-2 | The sidebar has a **History** view next to Projects (D20): the workspace's entries, newest first, grouped by day, each with method, name or URL, status and time; a filter field searches them. Choosing an entry opens it: its request is selected (or the scratch request, if it is gone) and the response panel shows that past response, marked with its time. "Restore request" puts that version of the request into the editor as unsaved edits. *(IDEA-5)* |
| R-HIST-3 | History can be cleared per project, or all at once. *(IDEA-5)* |
| R-HIST-4 | **A request's trend**: in the response line, small bars for the request's last 20 sends from history, oldest first, as tall as they took, failures (no response, 4xx, 5xx) in red; hovering says "Last 12 sends: 80 ms to 1.2 s, 2 failed" and when the bar under the pointer was sent, its status and time. Only with two sends or more, and only where history is kept. *(IDEA-84)* |
| R-HIST-5 | **Compare responses.** After a send, a chip next to the status says how much changed since the request's previous response ("3 changes", "Same as before"); it opens **What changed**: the status, time and size, the headers (Date and Age left out), and the body: JSON by structure and value with a `JSONPath` per change (added, removed, changed), other text by lines; at most 500 changes are listed. In the History view, an entry's menu has **Compare with the send before** (the same request's previous send that got a response), **Select for comparing** and **Compare with the selected one**; the older one is always "before". The comparison after a send is worked out off the UI thread. *(IDEA-82)* |

## Cookies

| ID | Requirement |
|---|---|
| R-CK-1 | Each collection has a cookie jar. Cookies from responses are stored in it and sent with later matching requests, like a browser does. On by default. |
| R-CK-2 | **Cookies can be disabled per request.** A disabled request sends no cookies from the jar and does not store cookies from its response. The setting is saved in the request file. |
| R-CK-3 | The cookie jar is local data (§6.7), never written to the collection directory. The jar can be cleared. |
| R-CK-4 | A `Cookie` header set manually on a request is always sent, even when the jar is disabled for that request. |
| R-CK-5 | **Cookie viewer**: the cookies in a project's jar, with value, domain, path, expiry and flags; single cookies can be removed. *(IDEA-6)* |
| R-CK-6 | **Cookies the response set.** The response panel has a **Cookies** tab next to Headers when the request sends and stores cookies (its own switch, R-CK-2, and "Send and store cookies" from the project, workspace or app, R-SET-1); otherwise there is no tab. It lists each `Set-Cookie` header of the response in order: name, value (full value on hover), where it is sent (`*.domain` with a `Domain` attribute, else "This host", plus its path; explained on hover), when it expires (local time, "Session", "Removes it" for a past date or `Max-Age` ≤ 0; `Max-Age` wins over `Expires`) and `Secure` / `HttpOnly` / `SameSite`. The tab counts the cookies; a response without any says so. A `Set-Cookie` value that can't be read is listed as such and turns the tab red. In a project, **Open the jar…** opens the cookie viewer (R-CK-5); the scratch request says its jar lasts until the app closes. Cookies set on redirect hops are in the jar, not in this tab. |

## Collections

| ID | Requirement |
|---|---|
| R-COL-1 | A collection is a named tree of folders and requests, with any nesting depth. |
| R-COL-2 | Create, rename, duplicate, move, and delete requests and folders. |

| R-COL-10 | **Command palette** (Ctrl+K, or Ctrl+Shift+P): every frequent action by name, with its shortcut: send, save, revert, copy as curl, new request in the current folder, switch environment, switch workspace, open environments, project defaults, settings, history, add project. Typing filters like quick open. *(IDEA-27)* |
| R-COL-12 | **Drag and drop in the tree**: drag a request or folder onto a folder to move it into it, or between two items to put it there; the order is saved like "Move up/down" (R-COL-3, R-GIT-6). | R-COL-11 | **Folder defaults**: a folder can define headers, auth and variables (in its `_folder.toml`), edited from the folder's menu. A request inherits from its folders, nearest first, then from the project: its own header replaces an inherited one with the same name; its auth is its own, else the nearest folder's, else the project's. Variables: local secret, then the active environment, then folder variables (nearest first), then project variables. | R-COL-13 | **Request tabs** (D31). Several requests are open at once in tabs above the editor; only requests open in tabs, not workflows. A single click (tree, quick open, history) opens the request in the *preview tab*: there is at most one, its title is in italics, and the next single click replaces it. Double-clicking the tab or the tree row keeps it open. Editing a request keeps its tab; sending does not. New, duplicated and saved-from-scratch requests open as kept tabs. Closing a tab never discards unsaved edits (they stay, as in R-COL-6). Tab menu: Keep open, Close, Close others, Close to the right, Close saved tabs; middle-click closes. A "⏷" list shows every open tab; Ctrl+Tab goes to the previously used tab, Ctrl+PageUp/PageDown to the neighbours, Ctrl+W closes the shown tab. Tabs follow renames and moves, and close when their request is deleted. Open tabs are local data per workspace (§6.7) and come back after a restart. *(IDEA-31)* |
| R-COL-14 | **Tabs grouped by project** (D32). Tabs of one project sit together after a chip with the project's name, in a colour worked out from the name; the project's row in the sidebar shows a dot in the same colour. Chips only show when tabs of two or more projects are open. Clicking a chip collapses the group to the chip (with a count) and expands it again; opening a request of a collapsed group expands it. The preview tab sits after all groups, with a stripe in its project's colour and, when it follows another project's tabs, its project's chip; it moves into its group when it is kept. The "⏷" list groups tabs by project. Collapsed groups are remembered with the tabs. |
| R-COL-15 | **Import an OpenAPI description** (D7, D33–D35) as a new project: servers become environments of one server, tags become folders, operations become requests with their parameters, example bodies and auth that uses secret variables. What can't be imported as written is listed before importing. *(IDEA-29)* |
| R-COL-16 | **Import a Postman collection** (v2.0 or v2.1 JSON; D7, D34, D36) as a new project: folders and requests in the same order and nesting; collection variables as project variables, folder variables and auth as folder defaults; a `{{variable}}` that starts request URLs as a server with its base URL in a "Default" environment; bearer, basic and API key auth with secret variables, whose values found in the file are kept in this machine's secret store only (D35); raw, form, multipart and GraphQL bodies; scripts kept as comments to port. What can't be imported as written is listed before importing. *(IDEA-10)* |
| R-COL-17 | **Import a `.http` file** (VS Code REST Client, JetBrains HTTP Client; D7, D34, D37) as a new project named after the file: a request per `###` block in file order, `@variables` as project variables, a base URL variable as a server with a "Default" environment (D36), `Authorization` and key headers as auth with secret variables whose values found in the file are kept in this machine's secret store only (D35), request variables (`{{login.response.body.$.token}}`) as captures, JSON, form, GraphQL and text bodies, handler scripts kept as comments. What can't be imported as written is listed before importing. |
| R-COL-18 | **Turn importers on and off** in the app's settings; all are on by default, also ones added later. One that is off is not offered, and a file recognised as that kind is refused. |

| R-COL-20 | **Import Postman environment files** (v2.1 JSON as Postman exports them, also wrapped in `{"environment": …}` as its API returns them; D49), several at once, from two places. In the **Postman collection import dialog** (R-COL-16), "Add environment files…" makes the files the new project's environments instead of "Default"; a server none of them sets keeps the collection's base URL, and the warning about a base URL without a value goes once every environment sets it. Each file becomes an environment named like it, or **updates the environment with that name**: what the file sets replaces, what it doesn't is kept. The Environments dialog opens afterwards only when a secret still has no value in some environment. A globals file or a collection given here is refused with a hint, and a collection entry given an environment file says where it goes. Both entries follow the Postman importer's switch (R-COL-18). *(IDEA-47)* |

## Collaboration through git

### On-disk format

Example layout:
```
my-api/                    # collection root, typically inside the API's git repo
  tortuga.toml             # manifest: name, format version, servers, collection variables
  environments/
    dev.toml
    staging.toml
  users/                   # a folder
    _folder.toml           # optional: folder display name and position (seq)
    list-users.toml
    create-user.toml
```
Example manifest and environment:
```toml
# tortuga.toml
format = 1
name = "Acme API"
[[servers]]
id = "users"               # stable key used by requests; the name can change freely
name = "Users API"
[variables]                # collection defaults
api_version = "v2"
```
```toml
# environments/dev.toml
name = "Development"
seq = 1
[servers]
users = "http://localhost:8080"
[variables]
user_id = "42"
```
Example request file:
```toml
name = "Create user"
seq = 2
method = "POST"
server = "users"
url = "/users"
[[headers]]
name = "Accept"
value = "application/json"
[body]
kind = "json"
content = '''
{
  "name": "{{user_name}}"
}
'''
```

| ID | Requirement |
|---|---|
| R-GIT-1 | A collection is a directory and can live anywhere, inside or outside a git repo. Folders are directories. |
| R-GIT-2 | **One TOML file per request**, so concurrent edits to different requests never conflict. |
| R-GIT-3 | Output is deterministic, so saving an unchanged request never modifies its file. Key order is fixed, and only fields that differ from their defaults are written. |
| R-GIT-4 | Shared files hold only shared data. No timestamps, response history, window/UI state, cookies, or secret values. |
| R-GIT-5 | File names come from request names (e.g. `create-user.toml`). Renaming a request renames its file, so git sees a rename. |
| R-GIT-6 | Order is stored as a `seq` number in each request file, not in a central list, so two people adding requests don't both edit the same file. |
| R-GIT-7 | The collection manifest `tortuga.toml` holds a `format` version. Newer app versions migrate older formats. If a file uses a newer format than the app understands, it is shown read-only. |
| R-GIT-8 | Files are hand-editable. A file that fails to parse (e.g. it contains merge-conflict markers) is shown as an error on that item only; the rest of the collection still loads. |

| R-MOCK-1 | **Examples on a request** (D44). | R-MOCK-2 | **Mock server.** "Start mock server" (project menu and command palette) serves the project's examples on `127.0.0.1`, on the port it last used or else the first free one from 4010 (kept per project in local data; changed in the mock server dialog). "Stop mock server" ends it; the project row shows `mock :<port>` while it runs, and closing the project stops it. An incoming request is answered by a saved request with the same method whose URL path, after its server's base URL (or after the scheme and host, or a leading `{{variable}}`, for requests without a server), matches: `:name` and `{{name}}` segments match any one segment, and the request with more literal segments wins, then the first in the tree. With several servers, a path that starts with `/<server id>` is matched against that server's requests first. The answer is the chosen example's status, headers and body, with `{{variables}}` filled from the active environment (never secret values); an example HTTP can't carry is a `500` saying why. With no matching request, a match without examples, or no example whose conditions hold, the answer is `404` with a JSON body giving the reason and the closest requests, so a developer sees what is not defined yet. Matching lives in `tortuga-core` (it compiles for wasm); the listener is native only, on `hyper` (D46). The mock listens on localhost only and contacts no other host (R-P-4). In the app it serves the files as they are on disk: a saved edit or a `git pull` changes the next answer. |
| R-MOCK-3 | **Choosing an example.** Of a request's examples, the first in file order whose `match` conditions all hold answers: `query` and `headers` (name and value), and `body` (a JSONPath (R-HTTP-13) or `xpath:` (R-HTTP-19) expression with the value it must have). An example without conditions matches anything, so the last one is the usual fallback. A request header `X-Tortuga-Example: <name>` picks an example by name, so a test can ask for the error case. `delay_ms` holds the answer back, to try slow responses. |
| R-MOCK-4 | **Sending to the mock** (D45). While a mock runs, the environment picker and the command palette offer **Mock (port N)**: an environment that is never saved, in which every server's base URL is its project's mock (under `/<server id>` when the project has several servers) and the variables keep the values of the environment chosen before. The **mock server dialog** (project menu → "Mock server (port N)…") shows whether it runs and on which port, starts, stops or moves it to another port, offers "Send requests here", and lists what it received, newest first: time, status, method and path, and the request and example that answered, or why nothing did (the last 500). |
| R-MOCK-5 | **Mocks in automated tests.** `tortuga-cli mock <project> [--port N] [--env NAME]` serves the mock (default port 4010) until stopped (Ctrl+C) and prints one line per request it answers. `tortuga-cli run <project> [target] --mock [--port N]` starts the mock on a free port, runs the workflow, folder or request with every server pointing at it (as R-MOCK-4, with the variables of `--env` if given) and stops it again, so a workflow's tests run in CI against the API as designed, before it exists. | R-MOCK-6 | **Examples from OpenAPI.** The OpenAPI import (R-COL-15) turns each operation's responses into the request's examples: each named example of the preferred media type (JSON first) under its key, else one from `example` or built from the schema, named by the code; a response without content gives an example without a body; `4XX`-style codes become `400`, `default` is left out. | R-MOCK-8 | **Contract check** (D47). After a response to a request that has examples (R-MOCK-1), it is compared with the example it should match: of the examples with the response's status, the first whose `match` conditions (R-MOCK-3) hold for the request as sent, else the first. Compared: the **status** is one of the examples' (otherwise "Status 500 is not one of the examples' (200, 404)"); the **Content-Type**'s media type (case and parameters ignored) is the example's, when the example has a Content-Type header or a body (then guessed as in R-MOCK-2); and for JSON, the **shape**: every key of an example object is in the response with a value of the same JSON type (string, number, boolean, array, object), a key the response has and the example lacks is reported too, `null` in the example accepts any value, and every element of a response array is checked against the example array's first element. | R-I18N-2 | Every text of the app's own UI is translated: menus, buttons, labels, tooltips, hints, dialogs and notices. English is the source and the fallback for any missing text. ## VS Code

| ID | Requirement |

| R-VSC-1 | **Tortuga projects in VS Code's Testing view** (D67). An extension in `editors/vscode` lists every folder with a `tortuga.toml` in the window as a project, with its workflows, folders and requests in the app's order, read through `tortuga-cli list <project>` (JSON), so the extension never re-implements how a project is read. The tree follows the files as they change. *(IDEA-97)* |

Each request passes or fails with its failed tests, errors and data rows as messages; a project runs every request, then every workflow. A second profile, **Run against the mock**, adds `--mock`. A missing `tortuga-cli` shows on the project with the setting to fix it. |
| R-VSC-3 | **Open in Tortuga.** `tortuga [PATH]` opens the project that holds PATH (a project folder or a file in one), adding it to the workspace, and a request file in a tab; the extension's code lens, explorer menu and command start it. |
